eDIDIO S10 Protocol APIv1.3.2

Google Protocol Buffer message reference for the eDIDIO S10 controllers and the ADDICT V3 — Getting started (README) · Changelog · Repository

At a glance

  • Discovery: UDP broadcast on port 30303
  • Control: TCP 23 or TLS 443
  • Framing: 0xCD + 2-byte big-endian length + protobuf-encoded EdidioMessage
  • Heartbeat: send something - an AytMessage if nothing else - within 20 s to keep the connection
  • Protocol version: 1.3.2 = 0x010302; devices report theirs in diag_system.proto_version

New here? Start with Requests and replies.

Requests and replies

How a request works

  • Every message, both ways, is one EdidioMessage with exactly one payload field set. On TCP (port 23) or TLS (443) it is framed as 0xCD, the protobuf length as two bytes (big-endian), then the protobuf bytes.
  • message_id is yours: the device copies it into its reply, so you can match replies to requests and have several in flight.
  • Commands (set a level, store configuration, run an action) are answered with an AckMessage: SUCCESS, or why not - INVALID_PARAMS (a value was refused), INDEX_OUT_OF_BOUNDS, UNEXPECTED_CASE / UNEXPECTED_TYPE (not supported by this device or firmware), UNAUTHORISED / FORBIDDEN (see roles). detail can carry a RejectReason.
  • Reads are answered with data: admin_message GETs come back as an admin_message with the value filled in; read_device, spektra_read and diag_message come back as the payload for what was asked for. The tables below list every reply.
  • Keep-alive: send something - an ayt_message if nothing else - within 20 seconds, or the device closes the connection.
  • Roles: with the device's secure session on, a connection must log in (admin_message GET NONCE, then secure_login) and each request needs a role: NONE < CONTROL < CONFIG < ADMIN. Too low gives FORBIDDEN, not logged in UNAUTHORISED. With it off nothing is checked. The ADDICT has no login.
  • Devices: the eDIDIO S10 controllers handle everything below unless marked; the ADDICT V3 handheld (over its Wi-Fi) handles the rows marked ADDICT. The tables describe eDIDIO firmware 1.6.3 and ADDICT firmware 3.9.3. Earlier firmware handles less: the ADDICT speaks this protocol from 3.8.8, and its Wi-Fi properties need 3.9.2 or later (WIFI_DIAGNOSTICS and DALI bus power 3.9.3). A device answers a message or property it does not have with UNEXPECTED_TYPE or UNEXPECTED_CASE, so check diag_system.firmware first if a feature matters.
  • Compatibility: fields are only ever added. An older device ignores a field it does not know, and a field it does not send reads as its default (0, false, ""), so treat 0 as "not reported" where the field says so.

Examples

Each request with its frame as sent on the socket (start byte and length included).

The three you will use most - a DALI command, DMX levels and an external trigger - can be built in SpektraPlus: Device Tools → Message Generator. Fill in the fields and it gives the bytes, start byte and length included, as decimal or hex, ready to paste into another system.

Set a DALI arc level

A command: the device answers with an AckMessage.

Request
EdidioMessage {
  message_id: 1
  dali_message {
    line_mask: 0b0001        // line 1
    address: 5               // short address
    custom_command: DALI_ARC_LEVEL
    arg: 200                 // arc level 0-254
  }
}
cd 00 0e 08 01 92 01 09 08 01 10 05 30 00 48 c8 01
Reply
EdidioMessage {
  message_id: 1
  ack { payload: SUCCESS }
}
cd 00 06 08 01 12 02 08 05

A field holding its default (0, false, "", the first enum value) is normally not sent at all. custom_command is the exception here: it is one choice of the action oneof, and a oneof field is always sent once chosen - so DALI_ARC_LEVEL (0) appears as 30 00.

Set DMX levels

A dmx_message sets consecutive channels on one or more universes, with an optional fade. channel is the first channel (1-512); level holds one value per channel and is repeated repeat times - here one RGB fixture set to red over 250 ms.

Request
EdidioMessage {
  message_id: 2
  dmx_message {
    universe_mask: 0b0001    // universe 1
    channel: 1               // first channel, 1-based
    repeat: 1                // one fixture
    level: [255, 0, 0]       // R, G, B
    fade_time_by_10ms: 25    // 250 ms
  }
}
cd 00 13 08 02 a2 01 0e 10 01 18 01 20 01 2a 04 ff 01 00 00 30 19
Reply
EdidioMessage {
  message_id: 2
  ack { payload: SUCCESS }
}
cd 00 06 08 02 12 02 08 05

Fire a trigger

An external_trigger runs any action a button or schedule could: the TriggerMessage names the TriggerType, and target_index / value / line_mask mean what that type says. Here it starts list 0 (lists count from 0).

Request
EdidioMessage {
  message_id: 3
  external_trigger {
    trigger {
      type: LIST_START
      target_index: 0        // list 0
    }
  }
}
cd 00 09 08 03 aa 01 04 0a 02 08 09
Reply
EdidioMessage {
  message_id: 3
  ack { payload: SUCCESS }
}
cd 00 06 08 03 12 02 08 05

Read a property

An AdminMessage GET comes back as an AdminMessage with the value filled in - here the device name, in data.string_data (the admin property table says which field each property uses).

Request
EdidioMessage {
  message_id: 4
  admin_message {
    command: GET
    target: DEVICE_NAME
  }
}
cd 00 07 08 04 8a 02 02 08 01
Reply
EdidioMessage {
  message_id: 4
  admin_message {
    command: GET
    target: DEVICE_NAME
    data { string_data: "Lobby" }
  }
}
cd 00 10 08 04 8a 02 0b 08 01 1a 07 1a 05 4c 6f 62 62 79

Change a property

A SET carries the new value in the same field and is answered with an AckMessage; INVALID_PARAMS if the value is refused.

Request
EdidioMessage {
  message_id: 5
  admin_message {
    command: SET
    target: DEVICE_NAME
    data { string_data: "Foyer" }
  }
}
cd 00 0e 08 05 8a 02 09 1a 07 1a 05 46 6f 79 65 72
Reply
EdidioMessage {
  message_id: 5
  ack { payload: SUCCESS }
}
cd 00 06 08 05 12 02 08 05

Ask what the device supports

A diag_message of type DIAGNOSTIC_SYSTEM_INFO returns diag_system: firmware and hardware versions, how many lists, alarms, sensors and so on it has, and proto_version - the protocol version it was built against.

Request
EdidioMessage {
  message_id: 6
  diag_message {
    type: DIAGNOSTIC_SYSTEM_INFO
  }
}
cd 00 05 08 06 82 02 00
Reply
EdidioMessage {
  message_id: 6
  diag_system {
    firmware: "..."
    proto_version: 0x010302   // 1.3.2
    ...
  }
}

Gate a feature on the protocol version: if (proto_version >= 0x010302) (1.3.2). Decode it as major = v >> 16 & 0xFF, minor = v >> 8 & 0xFF, patch = v & 0xFF. 0 means the firmware predates the field.

Read configuration back

A read_device request comes back as the payload for the ReadType asked for - here the physical inputs of profile 0, as inputs.

Request
EdidioMessage {
  message_id: 7
  read_device {
    type: INPUTS
    profile: 0
  }
}
cd 00 05 08 07 8a 01 00
Reply
EdidioMessage {
  message_id: 7
  inputs { ... }   // InputMultiMessage
}

AckMessage

Sent in Response to another message.

FieldTypeLabelDescription
payload AckMessageType

Will either indicate 'Success' or a particular Error as specified by "AckMessageType"

detail uint32

Optional context. Interpretation depends on payload type: for PARTIAL_SUCCESS on a DALI multi-line command it is the bitmask of lines that succeeded; for an ERROR payload (e.g. INVALID_PARAMS) it is a RejectReason code naming the specific reason (0 = unspecified); for a SUCCESS ack to a secure login it is the granted clearance level (0=NONE, 1=CONTROL, 2=CONFIG, 3=ADMIN).

RejectReason

Refines an ERROR AckMessageType with a specific, machine-readable reason, carried in AckMessage.detail

(detail stays a uint32 - for SUCCESS / PARTIAL_SUCCESS it keeps its existing meaning, e.g. a line bitmask).

app never drift. Values are allocated in 1000-wide blocks per subsystem - add new reasons to the owning

block, never renumber (gaps are free). uint32/varint: a value stays 2 wire-bytes up to 16383, and the field

itself reaches ~4.29e9, so the block scheme is effectively open-ended.

SpektraManifestMessage

Compact summary of which slots of a Spektra slot table hold data, and a change

Lets a client read only the slots that exist instead of polling every slot: a

may not be reflected. That is correct for a change detector; do not treat the

GpioPhase1Result

Raw Phase-1 GPIO classification — TX/RX as input with internal pull-down, EN as

output low (DMX transceiver receive mode), 16 samples OR-folded over ~8 ms.

Multi-sampling matters: a single read of RX on a line being actively driven by an

external DMX master can land inside a BREAK or 0-bit and falsely report EMPTY.

OR-folding 16 samples across one DMX frame's worth of time guarantees we observe

at least one MARK state if the line is active.

Why each pattern occurs:

EMPTY: nothing fitted, internal pull-downs win on both pins

DALI_LIKE: TX pulled to ~2 V by the on-board 3V3 → opto-LED → R4 (390R) bleed-through

regardless of DALI bus state. RX may be 0 or 1 depending on whether the

DALI bus is energised — TX HIGH alone is enough to classify.

DMX_LIKE: DMX line transceiver receiver enabled (EN=LOW) drives R output push-pull HIGH via the

transceiver's internal fail-safe biasing on undriven A/B. TX stays LOW

because the D input is high-Z CMOS.

CAUTION: this pattern is ALSO matched by a DALI daughterboard whose TX

bleed-through path is broken (R4 open, TX-opto LED open, daughterboard

3V3 lost on the TX-side feed) while R2's RX pull-up is still alive — that

case is what `dmx_toggle` exists to disambiguate.

DaliEchoResult

DALI active self-echo probe (~13 ms total, GPIO-only). Drives TX HIGH (DALI idle),

settles 10 ms (covers worst-case ~9 ms DALI bus rise time on fully-loaded buses),

reads RX. Then TX LOW for ~200 µs (active sink — well below any DALI receiver's

frame-start threshold so no devices misinterpret it) and reads RX. Then TX HIGH

again and reads RX. A healthy DALI board on a powered (~16 V) bus shows the

sequence (rx_idle=0, rx_during=1, rx_after=0) because the receive opto's

conduction tracks bus voltage.

PASS is a UNIQUELY POSITIVE identification of a healthy DALI loop on a powered bus

— no other fitted hardware can produce this echo pattern. Always run regardless of

Phase 1's classification so cross-checking can catch P1 misclassifications.

FAIL does NOT localise to a specific failure — could be a damaged DALI board, an

unpowered/disconnected DALI bus, a shorted bus, or a non-DALI daughterboard.

SKIPPED means the echo did not run. Two causes, distinguishable by the rest of the

entry:

- RX was observed toggling in the ~1 ms pre-check immediately before this phase,

i.e. an external DMX master is transmitting. Driving TX into a line another

transmitter owns is unsafe, and the result would be meaningless anyway: a BREAK

sampled as rx_idle followed by a data MARK can forge the (0, 1, 0) signature.

Here gpio_phase1 and verdict still carry real results.

- The whole probe was skipped because the line was locked by DALI or RDM traffic.

Here gpio_phase1 and verdict are both UNKNOWN and every phase reads SKIPPED.

To rule out the forged-signature case the echo is repeated three times back-to-back

and only reports PASS when all three agree.

DmxToggleResult

DMX EN-toggle probe (~7 ms total, GPIO-only). Holds TX OUTPUT HIGH (so if the driver

were enabled it would output DMX idle A=HIGH/B=LOW — minimally disruptive), RX as

input pull-down. EN goes LOW (receiver enabled) then HIGH (receiver disabled, driver

briefly enabled for ~10 µs) then back LOW. Only a real DMX transceiver R output transitions

from push-pull HIGH → high-Z in this sequence. A DALI board's RX is held HIGH by R2

(4k7 to on-board 3V3) regardless of EN, so it gets stuck HIGH on both reads. Empty

slot reads (0, 0).

fitted hardware can produce the high→high-Z transition. Always run regardless of

Phase 1's classification so cross-checking can catch P1 misclassifications.

- dali_echo already returned PASS. The board is positively identified as DALI and

the verdict no longer depends on this phase, so it is not run.

- RX was observed toggling (active external master) during the ~1 ms pre-check run

immediately before this phase. Skipping protects against driving the line into

contention with an external master mid-frame.

- The whole probe was skipped because the line was locked by DALI or RDM traffic,

in which case verdict is UNKNOWN and every phase reads SKIPPED.

LineDiagnosticVerdict

Synthesized verdict from (configured_as, gpio_phase1, dali_echo, dmx_toggle, dmx_listen).

Verdict logic prefers the strongest positive signal:

1. dali_echo == PASS → DALI confirmed (regardless of P1)

2. dmx_toggle == PASS → DMX confirmed (regardless of P1)

3. dmx_listen == DMX_VALID → a coherent DMX512 stream is positive proof of a working

receive path, obtained passively. Ranks below the EN-toggle, which proves the

control path as well, but above any P1 inference.

4. none of those → fall back to P1 + the FAIL/SKIPPED context

This protects against P1 misclassifications — e.g. a damaged DMX board whose TX pin

leaks high reads as DALI_LIKE under P1, but the EN-toggle correctly identifies it.

Failure modes deliberately NOT distinguished by this verdict (firmware can't see them

from the three pins available): DALI bus open vs. shorted; DALI cable mis-wired into

a DMX board (looks like quiet DMX); DMX cable mis-wired into a DALI board (looks

like unpowered DALI bus); DMX board with lost on-board 3V3 (looks like EMPTY unless

the operator configured the slot as DMX, in which case EMPTY_OR_UNPOWERED_BOARD).

AdminStorageDiagnosticsMessage

Storage subsystem health. Returned for AdminMessage{GET, STORAGE_DIAGNOSTICS}.

Scope is the storage SPI bus and every device on it - the SD card, the NOR

flash and the IO expander share the bus, so one device wedging it takes the

others down. The bus fields come first because they are the context the device

fields are read in.

All counters are absolute since boot, never cleared; diff successive GETs for

a rate. Only the four sd_*_abort_* counters saturate at 0xFFFFFFFF (a value

there is a lower bound); the rest are plain 2^32 wraps.

Side-effect-free: every field is a RAM latch, nothing probes the bus, so this

is safe to poll.

Read the crash/reset record captured from backup SRAM at boot.

The device captures a 128-byte crash record into battery-backed SRAM on
