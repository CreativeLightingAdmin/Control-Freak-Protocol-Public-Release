Protocol Reference

eDIDIO S10 Protocol APIv1.3.1

Google Protocol Buffer message reference for the eDIDIO S10 controller — Getting started & examples (README) · Repository

At a glance

  • Discovery: UDP broadcast on port 30303
  • Control: TCP 23 or TLS 443
  • Framing: 0xCD + 2-byte big-endian length + protobuf-encoded EdidioMessage
  • Heartbeat: send AytMessage (0xFF 0xF6) within 20 s to keep the link alive

See the README for the full guide, framing walkthrough and language examples.

AdminEthernetDiagnosticsMessage

Returned in response to AdminMessage{GET, ETHERNET_DIAGNOSTICS}.

All PHY register fields are live reads via MDIO at the moment of the

request (except SECR — symbol error count is self-clearing on read and

is accumulated in phy_symbol_errors_total).

MAC counters are the Ethernet MAC's MMC registers (32-bit, not self-clearing by

default on this build). They are absolute since power-on; clients should

take two snapshots and diff to get a rate. They WILL wrap eventually

(~8 hours at 100 Mbps line-rate of 64-byte frames).

secr_saturation_count uint32

SECR (PHY reg 0x1A) is a 16-bit self-clearing counter. If the symbol error rate exceeds 65535 between successive drains, the register saturates at 0xFFFF and we lose count fidelity for the overflow. This counter increments every time we drain SECR and find exactly 0xFFFF — i.e. every time we know we under-counted. A non-zero value means the phy_symbol_errors_total / per-minute histogram are LOWER BOUNDS only.

uptime_seconds uint32

peak_secr_per_tick uint32

===== Burst tracking ===== Largest single-drain SECR value ever observed since boot. The diagnostics module drains SECR on a periodic timer (~4 Hz / 250 ms by default) AND on every PHY poll tick (~1 Hz). The field name is kept for wire compatibility; treat it as "peak_secr_per_drain". If this approaches 0xFFFF (= 65535) the chip saturated the counter and we lost precision — see secr_saturation_count.

current_minute_secr uint32

SECR count accumulated in the CURRENTLY-OPEN minute bucket (i.e. the bucket that will eventually be appended to `buckets` when the minute rolls). 0 to ~10s for a brand-new minute, up to ~1.8M/min at observed peak rates.

current_minute_index uint32

Uptime-minute index of the currently-open bucket — clients use this to know which minute the partial `current_minute_secr` belongs to.

events EthLinkEventRecord repeated

===== Ring buffer of recent link-state transitions, oldest -> newest =====

buckets EthErrorHistogramBucket repeated

===== Per-minute error histogram, oldest -> newest ===== Each bucket is a closed (finalised) 1-minute window. The currently accumulating minute is exposed via current_minute_* above. Up to 30 minutes of history so you can leave the device running and see patterns (thermal drift, time-of-day EMI, traffic correlation).

phy_regs_all uint32 repeated

===== Full Ethernet PHY register dump (live MDIO sweep) ===== 32 entries indexed by PHY register address (0..31). Reserved/unused registers will read back as 0 (or whatever the chip drives onto MDIO for those addresses). Included primarily for forensic comparison against the PHY datasheet when needed.

DaliEchoResult

DALI active self-echo probe (~13 ms total, GPIO-only). Drives TX HIGH (DALI idle),

settles 10 ms (covers worst-case ~9 ms DALI bus rise time on fully-loaded buses),

reads RX. Then TX LOW for ~200 µs (active sink — well below any DALI receiver's

frame-start threshold so no devices misinterpret it) and reads RX. Then TX HIGH

again and reads RX. A healthy DALI board on a powered (~16 V) bus shows the

sequence (rx_idle=0, rx_during=1, rx_after=0) because the receive opto's

conduction tracks bus voltage.

PASS is a UNIQUELY POSITIVE identification of a healthy DALI loop on a powered bus

— no other fitted hardware can produce this echo pattern. Always run regardless of

Phase 1's classification so cross-checking can catch P1 misclassifications.

FAIL does NOT localise to a specific failure — could be a damaged DALI board, an

unpowered/disconnected DALI bus, a shorted bus, or a non-DALI daughterboard.

DmxToggleResult

DMX EN-toggle probe (~7 ms total, GPIO-only). Holds TX OUTPUT HIGH (so if the driver

were enabled it would output DMX idle A=HIGH/B=LOW — minimally disruptive), RX as

input pull-down. EN goes LOW (receiver enabled) then HIGH (receiver disabled, driver

briefly enabled for ~10 µs) then back LOW. Only a real DMX transceiver R output transitions

from push-pull HIGH → high-Z in this sequence. A DALI board's RX is held HIGH by R2

(4k7 to on-board 3V3) regardless of EN, so it gets stuck HIGH on both reads. Empty

slot reads (0, 0).

PASS is a UNIQUELY POSITIVE identification of a working DMX receiver — no other

fitted hardware can produce the high→high-Z transition. Always run regardless of

Phase 1's classification so cross-checking can catch P1 misclassifications.

SKIPPED happens when RDM is in flight on this line OR when RX was observed toggling

(active external master) during a brief pre-check. Skipping protects against driving

the line into contention with an external master mid-frame.

GpioPhase1Result

Raw Phase-1 GPIO classification — TX/RX as input with internal pull-down, EN as

output low (DMX transceiver receive mode), 16 samples OR-folded over ~8 ms.

Multi-sampling matters: a single read of RX on a line being actively driven by an

external DMX master can land inside a BREAK or 0-bit and falsely report EMPTY.

OR-folding 16 samples across one DMX frame's worth of time guarantees we observe

at least one MARK state if the line is active.

Why each pattern occurs:

EMPTY: nothing fitted, internal pull-downs win on both pins

DALI_LIKE: TX pulled to ~2 V by the on-board 3V3 → opto-LED → R4 (390R) bleed-through

regardless of DALI bus state. RX may be 0 or 1 depending on whether the

DALI bus is energised — TX HIGH alone is enough to classify.

DMX_LIKE: DMX line transceiver receiver enabled (EN=LOW) drives R output push-pull HIGH via the

transceiver's internal fail-safe biasing on undriven A/B. TX stays LOW

because the D input is high-Z CMOS.

CAUTION: this pattern is ALSO matched by a DALI daughterboard whose TX

bleed-through path is broken (R4 open, TX-opto LED open, daughterboard

3V3 lost on the TX-side feed) while R2's RX pull-up is still alive — that

case is what `dmx_toggle` exists to disambiguate.

LineDiagnosticVerdict

Synthesized verdict from (configured_as, gpio_phase1, dali_echo, dmx_toggle, dmx_listen).

Verdict logic prefers the strongest positive signal:

1. dali_echo == PASS → DALI confirmed (regardless of P1)

2. dmx_toggle == PASS → DMX confirmed (regardless of P1)

3. neither PASS → fall back to P1 + the FAIL/SKIPPED context

This protects against P1 misclassifications — e.g. a damaged DMX board whose TX pin

leaks high reads as DALI_LIKE under P1, but the EN-toggle correctly identifies it.

Failure modes deliberately NOT distinguished by this verdict (firmware can't see them

from the three pins available): DALI bus open vs. shorted; DALI cable mis-wired into

a DMX board (looks like quiet DMX); DMX cable mis-wired into a DALI board (looks

like unpowered DALI bus); DMX board with lost on-board 3V3 (looks like EMPTY unless
